# 실제 클라우드 E2E 실행 기록 (2026-11-07 ~ 11-08)

chiikawa 앱(FastAPI API 4 + worker 2 프로세스, 두 환경 각각)을 실제 AWS(ap-northeast-2)와 GCP(asia-northeast3) 사이에서 옮긴 기록입니다. 수치는 모두 플랫폼의 DynamoDB 기록(`foxtrot-control-plane`, `foxtrot-db-operator`)에서 2026-11-08 13:10 KST에 읽었고, 발췌는 [2026-11-07-08-runs.json](2026-11-07-08-runs.json)에 있습니다. 시각은 UTC입니다(KST = +9h).

관리형 서비스를 그대로 썼습니다. DB는 RDS PostgreSQL 17 ↔ Cloud SQL PostgreSQL 17, 캐시는 ElastiCache ↔ Memorystore, 오브젝트는 S3 ↔ GCS, 트래픽은 Cloudflare Load Balancer의 pool 가중치, 앱 VM은 provisioner가 만든 EC2·GCE입니다. 네 자원 모두 앱이 고정 프록시(PgBouncer, Redis 프록시, 오브젝트 라우팅)를 통해 접속한 상태에서 전환했습니다.

앱 입장의 정지는 더 깁니다. 오케스트레이터가 업무 HELD 근거를 확인한 시각부터 RESUME 뒤 RUN으로 돌린 시각까지는 wf-55a54889 6.7 s, wf-32f75936 10.3 s, wf-93f2a371 6.5 s였습니다. DB 자체 정지 1.4 s와의 차이는 QUIESCE → CUTOVER → RESUME 세 명령 사이의 오케스트레이션 간격이며, 다음 단축 대상입니다.

## wf-a6541981: 오브젝트와 Redis (11-07)

## 이 기록이 말하지 않는 것

- 정지 중 쓰기 손실 0건은 barrier LSN과 적용 origin LSN으로 보였고, 전체 row 비교는 하지 않았습니다(설계상 제거).
- 합성 probe의 비율은 실제 사용자 트래픽 비율이 아니고, 실 사용자 요청의 5xx는 집계하지 않았습니다.
- 같은 환경 쌍에서 각 1회 실행이라 재현성·상한을 주장하지 않습니다.

## 미해결

- GCP → AWS의 START_SYNC(RDS subscriber의 CREATE SUBSCRIPTION)가 UNKNOWN을 반복한 원인.
- 앱 정지(6.5~10.3 s)와 DB 정지(1.4 s)의 차이인 QUIESCE/CUTOVER/RESUME 명령 간 간격.
- 업무 probe의 재고 소진(join 500)이 게이트에 섞이는 문제.
